## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Create fixtures/t1-plan-conformance/ as an isolated Go module (own go.mod, mise.toml, Taskfile.yml, README.md), mirroring fixtures/t1-benchmark-harness/'s shape: a small library package (conformance) plus a CLI (cmd/t1conform). Not a root production module; not imported by anything under prototype/bootstrap or the future cmd/internal/pkg tree.

2. Canonical golden format: plain JSON documents (NOT Go structs representing "the" plan schema - defining typed Go values for Plan/Node/Artifact would itself stabilize a schema pre-Gate-1, which roadmap section 3 rule 3a and section 24 item 8 forbid). Each golden carries the same fixture_id/version/status header convention as fixtures/w1/w2/w3, plus its own harness-envelope version (e.g. "t1-plan-conformance-v1").
   - goldens/w1-fast-project-check.plan.json - references fixture_id "w1-fast-project-check" (fixtures/w1/manifest.yaml), covering the subset of E02's required plan concepts that plausibly apply to W1 (typed artifacts/outputs, planning condition, outcome condition, resource requirements, execution profile, cache policy).
   - goldens/w2-cross-target-artifact-pipeline.plan.json - references fixtures/w2/graph.json's fixture_id, adding cross-target execution-profile variation.
   - goldens/w3-isolated-native-mobile-stack.plan.json - references fixtures/w3/spec.md's fixture_id, adding a service endpoint.
   - goldens/synthetic-full-coverage.plan.json - not tied to any single W-fixture; a synthetic graph deliberately exercising every field E02's own fixture requirement lists (typed artifacts, optional outputs, planning condition, outcome condition, resource requirements, execution profile, cache policy, secret capability reference, service endpoint, and an effect) in one place, since W1-W3 individually don't naturally need all of them (secrets/effects show up more in later tranches).

3. conformance package:
   - Canonicalize(candidate json.RawMessage) ([]byte, error): normalizes order-irrelevant structures (e.g. sorts a nodes array by stable node id, sorts dependency lists) before re-marshaling with sorted object keys and no insignificant whitespace - this is what makes "declaration reordering that is semantically irrelevant" (E02) not affect the digest, while a real content change still does.
   - Digest(canonicalBytes) string: SHA-256 hex, for AC #2's repeat-generation byte-equivalence check.
   - Validate(candidate) []Violation: checks protocol/schema version compatibility (unknown/missing version is an explicit rejection, not a silent pass), and that every reference (node dependency, artifact consumption, effect target, etc.) resolves to a declared entity in the same document - unknown fields also rejected (strict decoding, no silently-ignored extra data).
   - Compare(candidate, golden) []Diff: structural diff between two canonicalized documents; each Diff carries a JSON-Pointer-style semantic path (e.g. /nodes/2/consumes/0/ref) and old/new values, satisfying AC #4.

4. cmd/t1conform CLI: takes --candidate <file> --golden <file> [--diff-out <dir>], validates the candidate, canonicalizes both, compares digests, and on any failure writes diff.json plus copies of both inputs to --diff-out (mirroring t1bench's raw-evidence-trail pattern) so a failure is reproducible without rerunning anything live.

5. Self-test fixtures under testdata/ (mirroring how fixtures/w1 shipped 3 deliberately-broken repo variants to prove its own gate isolates failures correctly) - each is a small candidate JSON plus an assertion of what the checker should do:
   - conformant: byte-identical structure to a golden after canonicalization -> passes, same digest.
   - reordered-but-equivalent: same nodes/dependencies in different declaration order -> same digest as the golden (proves reordering is actually ignored, not just claimed to be).
   - missing-version: version field absent -> rejected, semantic path names the missing field.
   - unknown-field: an extra undeclared field present -> rejected.
   - invalid-reference: a node consumes an artifact id that is never produced anywhere in the document -> rejected, semantic path names the dangling reference.
   - condition-changed: a planning condition's value changed from the golden -> digest differs (proves meaningful changes DO alter the digest, the complement of the reordering test).
   - Repeated-generation test: canonicalize the same golden input twice in one test, assert byte-for-byte identical output (process-independent determinism proxy, since no real candidate implementation exists yet to run in two real processes).

6. Verification: go build/vet/gofmt/test inside fixtures/t1-plan-conformance/; root mise exec -- task check unaffected (isolated module, no prototype changes).

7. README.md documents: the question this answers (E01/E02 comparability), why goldens are plain JSON not Go types, what "conformant" means today (no real candidate exists, so conformance is checked against this harness's own testdata self-tests, not a live E01/E02 output), and the reproduction command.
