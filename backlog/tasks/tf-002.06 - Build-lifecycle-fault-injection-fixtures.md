## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Build a new, isolated Go module fixtures/t1-lifecycle-faults/ (own go.mod, mirroring fixtures/t1-benchmark-harness's pattern - not a root production package, not importing prototype/bootstrap) implementing a small ABSTRACT durable-lifecycle simulation: an append-only in-memory journal of named events, a set of named checkpoints (admit, execute-start, execute-complete, cleanup-start, cleanup-complete, lease-acquire, lease-renew, lease-expire), and a fault-injection API that can trigger a named fault (process-crash, daemon-restart, worker-loss, cancellation, lease-expiry) at a declared checkpoint, before or after its durable transition commits (AC #2). This is deliberately abstract/generic (not tied to W2's build/test/inspect node names or W3's namespace/service records) because E05 itself is "a scheduler simulation with fake providers... do not execute real builds" (roadmap section 9) - there is no real daemon in this codebase to inject faults into, and the harness must not presume one.
2. Implement all 5 required scenarios as table-driven Go tests: process crash (mid-transition), daemon restart (journal reload after simulated process death - assert zero lost committed events, directly satisfying AC #4 and the roadmap's initial budget "no lost durable event after injected daemon restart"), worker loss, cancellation, and lease expiry. Each scenario's assertions follow the "Assertions a harness must implement" pattern already used in fixtures/w2/golden/worker-loss.md and fixtures/w2/golden/cancellation.md and fixtures/w3/examples/scenario-caller-loss.json's lease/orphan event sequence - but implemented as actual runnable checks, not prose.
3. Cross-reference, do not duplicate or modify: fixtures/w2/golden/worker-loss.md and cancellation.md (TF-002.02's territory, already landed) remain the pipeline-level (build/test/inspect) specification of what SHOULD happen; this ticket's harness implements the underlying abstract lifecycle mechanics (retry-from-scratch, no speculative downstream placement, bounded-window cleanup, no lost committed events) that those docs left as unimplemented TODOs, and its own scenario docs will explicitly link back to them. Same treatment for fixtures/w3/examples/scenario-caller-loss.json's lease-expiry/orphan-reclaim pattern.
4. Each scenario declares an explicit experimental version (roadmap rule 3a) and exposes: injection point (before/after transition), the resulting durable event sequence, a repeated-work count, cleanup/orphan result, and recovery outcome (AC #3), matching this ticket's own Observability requirement.
5. Write evidence: what's measured/reproducible now (the simulation's own deterministic assertions) vs. limitations (this is a simulation of abstract lifecycle mechanics, not a real daemon/scheduler - E05 will need to validate whether this abstraction actually matches whatever daemon design it eventually builds).
6. Verify: go build/vet/gofmt/test on the new module; root mise exec -- task check unaffected.
