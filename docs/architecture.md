# Architecture

## Objective

Taskflow executes a typed dependency graph across local and remote targets while
preserving the task aliases developers already use.

The first design constraint is durable correctness:

1. a node never runs before all required dependencies have succeeded;
2. successful work is not repeated during a compatible resume;
3. a cache hit is based on declared, inspectable identity;
4. the same pipeline definition has the same structural digest;
5. providers cannot silently change graph semantics.

## Component map

```text
Project pipeline (compiled Go)
            │
            ▼
       flow.Pipeline
            │ validate + fingerprint
            ▼
     engine.Scheduler ───────────────► event.Sink ──► terminal.Renderer
        │        │
        │        └───────────────────► state.Store
        │                               ├─ local files
        │                               └─ future shared store
        ▼
  cache coordinator ─────────────────► cache.Store
        │                               ├─ local CAS
        │                               └─ future object storage
        ▼
   runner.Registry
        ├─ Taskfile adapter
        ├─ Just adapter
        └─ direct command adapter
            │
            ▼ process.Spec
     target.Registry
        ├─ local provider
        ├─ Sprite provider
        └─ Orchard provider
            │
            ▼
      acquired environment
            │
            ▼
          process
```

The scheduler knows DAG state but knows nothing about Task, Just, Sprites, SSH,
or Tart. Runner adapters know command syntax but cannot select infrastructure.
Target providers execute portable process specs but cannot add dependencies.

## Typed pipeline definitions

A pipeline is ordinary Go code returning a validated `*flow.Pipeline`.

Functional options keep simple definitions terse while allowing reusable
functions:

```go
func goChecks(p *flow.Builder, task taskfile.Adapter) flow.Ref {
	return p.Step(
		"go-tests",
		task.Run("be:test"),
		flow.On("sprite"),
		flow.Inputs("backend/**/*.go", "backend/go.mod", "backend/go.sum"),
		flow.Outputs("backend/build/test-results/**"),
		flow.WithCache(flow.CacheReadWrite, "v1"),
	)
}
```

There is no general-purpose declarative pipeline format. JSON may appear in
internal state, event, or provider protocols, but it is generated by compiled
Go types rather than authored as the workflow.

### Loading project definitions

Go cannot safely load arbitrary source into an existing binary portably. The
planned CLI therefore treats a project-local `.taskflow` package as a compiled
driver:

1. hash its Go sources, module files, Taskflow version, and build platform;
2. reuse a previously built driver when the hash matches;
3. otherwise build it with the Go toolchain;
4. execute the driver through a versioned internal protocol.

This preserves `taskflow run verify` ergonomics without Go's platform-specific
`plugin` package or runtime source interpretation. The driver links provider
and adapter modules in-process, preserving compile-time type checking.

## Runner adapters

A runner adapter converts a structured `runner.Invocation` into a
`process.Spec`.

Examples:

```text
{adapter: taskfile, recipe: be:test}
    → task be:test

{adapter: just, recipe: test, args: [backend]}
    → just test backend
```

Resolution happens after target selection. The named runner must therefore be
installed in the target image.

Adapters are deliberately small and deterministic. They do not:

- execute commands;
- provision infrastructure;
- inspect or modify scheduler state;
- declare hidden distributed dependencies.

Taskfile-local dependencies can remain inside an opaque Taskflow node. When a
dependency needs individual placement, caching, retries, or graph visibility,
the edge moves to Taskflow and the invoked Task recipe must become a dep-free
leaf.

## Target providers

A provider implements three operations:

1. report capabilities;
2. acquire an environment for a run/step/resource request;
3. execute and release that environment.

`Acquire` does not mean "create a VM." A provider may:

- reuse the controller for the local target;
- wake or create a Sprite;
- select an existing Tart VM;
- ask Orchard to schedule a VM;
- retain a warm environment for a placement group.

Likewise, `Release` lets the provider pause, recycle, checkpoint, or destroy the
underlying environment.

### Initial providers

#### Local

Runs a child process below a workspace root. It is the reference implementation
and the fastest default.

#### Sprite

Expected responsibilities:

- create or wake a named Linux Sprite;
- materialize the source snapshot and cached outputs;
- execute commands through the Sprite API;
- stream output and exit state;
- checkpoint useful warm state independently of task-result caching;
- pause or retain the Sprite according to policy.

#### Orchard

Expected responsibilities:

- request a macOS Tart VM from Orchard with labels and resources;
- choose an OCI image containing Xcode/toolchains;
- execute through Orchard/SSH;
- transfer source and outputs;
- release or retain a warm VM.

The underlying Mac host may initially be a Scaleway bare-metal Mac mini.
Taskflow will speak to Orchard, not Scaleway, during normal node execution.
Host allocation is a separate fleet-management concern.

## Scheduler

The scheduler is a persistent state machine, not a recursive task walker.

```text
pending ──dependencies ready──► running ──exit 0──► succeeded
   │                              │
   │ dependency failed            └─exit nonzero─► failed
   ▼
 blocked
```

Independent ready nodes run up to the configured concurrency. A provider may
apply a lower capacity or finite-resource constraint.

Each transition is saved before dependent work becomes eligible. If the
controller crashes while a node is `running`, resume resets that node to
`pending`; a task must not be assumed successful without a committed success
record.

## Resume

Resume is keyed by run ID and guarded by the pipeline definition digest.

A resumed run:

- keeps `succeeded` nodes successful;
- resets `running`, `failed`, and `blocked` nodes to `pending`;
- schedules only nodes whose dependencies are now satisfied;
- rejects a changed pipeline definition by default.

Before remote production use, resume also needs an output-presence invariant:
a successful node may be skipped only if its declared outputs still exist in
the shared cache/artifact store. Otherwise it is safely re-queued.

Future controlled modes may allow migration across compatible graph changes,
but silent best-effort matching is explicitly out of scope.

## Caching

Taskflow distinguishes two concepts:

- **run state** answers whether a specific node succeeded in a specific run;
- **cache state** answers whether equivalent work has already produced reusable
  outputs in any compatible run.

The intended cache key includes:

```text
Taskflow cache schema version
pipeline + step identity
runner invocation
declared input content digests
dependency output digests
target OS + architecture
declared toolchain/image identity
selected environment values
explicit user cache version
```

Secrets are never stored in cache manifests. Nodes that mutate external state,
depend on undeclared ambient state, or publish releases are uncacheable.

The cache store deals in opaque content-addressed archives. A coordinator above
the provider is responsible for deterministic packing, restoration, and
manifest validation. This keeps cache semantics consistent across local,
Sprite, and Orchard targets.

## Workspaces and artifacts

The source checkout is captured as an immutable input snapshot for a run.
Remote steps receive that snapshot rather than independently choosing a Git
branch tip.

Declared outputs are the only supported cross-target filesystem dependency.
Shared mutable directories are not part of the distributed execution model.

Longer-lived same-target workflows, such as booting a simulator and then
running multiple iOS phases, will use an explicit placement/workspace group.
Affinity must be visible in the graph rather than inferred by a provider.

## Events and terminal output

The engine emits structured lifecycle events. The terminal renderer is one
consumer; JSON logs and OpenTelemetry can be additional consumers without
changing execution.

Planned verbosity:

- `quiet`: failures and final result;
- `normal`: one start/finish line per node plus summary;
- `verbose`: placement, cache decisions, retries, commands, and provider
  lifecycle;
- `trace`: internal scheduler and transfer diagnostics.

Output never requires cursor addressing or a full-screen TUI.

## Extension model

Taskflow extensions are normal Go modules compiled into the project driver:

```go
app.UseRunner(taskfile.New())
app.UseTarget(sprite.New(...))
app.UseCache(s3cache.New(...))
app.UseEvents(otel.New(...))
```

This avoids unstable dynamic loading and gives extensions the same compiler
guarantees as the pipeline.

Public extension contracts will remain deliberately small. Provider-specific
configuration belongs to provider packages rather than a universal options
map.

An out-of-process provider protocol may be added after the in-process contract
has real Sprite and Orchard implementations. It must be versioned and
capability-negotiated; it is not required for the first release.

## Security boundary

- Providers receive only the credentials required for their target.
- Cache and state stores never persist raw secrets.
- Release/signing steps can be pinned to trusted targets.
- Source snapshots and output manifests are digest verified.
- Remote command logs must support redaction before terminal or telemetry
  emission.
- Pipeline code is trusted project code. Executed task code is not assumed
  safe merely because a provider offers VM isolation.

## Deliberately deferred

- Web UI or TUI.
- Managed Taskflow control plane.
- GitHub status/check integration.
- Arbitrary YAML workflow import.
- Transparent migration of every nested Taskfile dependency.
- General distributed services or Kubernetes abstraction.
