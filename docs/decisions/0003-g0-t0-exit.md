# ADR 0003: G0 — T0 exit decision

Status: accepted

Question: does T0 (repository reset and prototype baseline) satisfy exit gate
G0, and may T1 (measurement contracts and representative fixtures) begin?

Decision date: 2026-09-02

Task: TF-001.05. Roadmap references:
[T0 evidence to capture and exit gate G0](../roadmap.md#7-t0-repository-reset-and-prototype-baseline),
[Risk Lab experiments](../roadmap.md#9-risk-lab-experiments),
[decision-record fields](../roadmap.md#21-decision-records).

## Context

TF-001.01 through TF-001.04 independently captured the T0 evidence-to-capture
list against `prototype/bootstrap` at source revision `9ddea88`
(macOS/arm64, Go 1.25.12): the gate-reproduction record, the package and
interface inventory with Fable-review-finding mapping, the W1-like graph size
and project-driver startup baseline, and the cache-ordering/local-interference
characterisation. This decision reviews all four against G0's five exit
criteria and assigns ownership and start order to the Risk Lab experiments
(E01-E08) so T1 has a concrete next step.

This is a gate decision about the *isolated prototype and the repository's
current state*, not a product design decision. It makes no claim about future
SDK, plan, cache, or protocol contracts.

## Options considered

1. **Pass G0 unconditionally** — accept all four evidence tickets as
   sufficient and unblock T1 immediately.
2. **Pass G0 with named residual risks recorded, not blocking** — accept the
   evidence, but explicitly record every gap the evidence surfaced (two Fable
   test-coverage gaps, four cache/acquisition-ordering questions handed to
   E04, single-platform-only measurement) as accepted residual risk rather
   than silently dropping them.
3. **Fail or narrow G0** — require additional prototype changes (e.g. new
   regression tests for the two Fable gaps, a Linux/amd64 reproduction, or a
   fix to the cache/acquisition ordering) before T1 may begin.

## Predeclared thresholds

From roadmap section 7, G0 passes when, and only when, all five hold:

1. the prototype builds and tests from its isolated directory;
2. no new root production package imports the prototype;
3. root documentation clearly distinguishes product proposals from prototype
   facts;
4. baseline measurements and commands are reproducible;
5. future experiment IDs and owners are assigned.

Nothing in this list requires the prototype's own test suite to be complete,
requires multi-platform reproduction, or requires the cache/acquisition
ordering problems E04 exists to investigate to already be fixed. Requiring
more than these five criteria would be scope creep on this gate; the
Risk Lab (E01-E08) is exactly where semantic-model and reproducibility risks
belong, not T0.

## Handling the evidence-surfaced gaps (option 2 chosen over option 3)

TF-001.02 and TF-001.04 each surfaced findings and explicitly asked this
ticket whether they block G0:

- **Two Fable-review test-coverage gaps** (TF-001.02 section 2, Medium #2 and
  #8: no test asserts retry-attempt/output-identity reset specifically on
  resume; neither `runner/taskfile` nor `runner/just` tests the
  runner-version cache-identity probe, and `runner/just` has no test file at
  all). **Decision: accepted residual risk, does not block G0.** These are
  gaps in the *frozen prototype's own* internal test coverage, not in T0's
  evidence about the prototype. Per `AGENTS.md` and roadmap section 3,
  prototype code changes only to preserve reproducibility, correct evidence,
  or support a named comparison — closing an internal coverage gap in code
  that will not be extended does not meet that bar. Recorded here so the
  gaps are not silently lost, not because they need a prototype patch.
- **Four cache/acquisition-ordering questions handed to E04** (TF-001.04,
  "Open questions handed to E04"): cache identity is not resolvable
  independently of environment acquisition; a cache hit still performs a full
  `Acquire`; local admission exclusivity is scoped to a single `Provider`
  instance rather than the filesystem root; corruption modes for non-atomic
  concurrent writes are unexplored. **Decision: not a G0 blocker — this is
  precisely R4/R5/R9's uncertainty (roadmap section 5, exposure 20/15/15) and
  exactly what E04 exists to resolve.** G0 does not require the prototype's
  cache-before-provision behavior to already be correct; it requires the
  behavior to be evidenced, which TF-001.04 did. E04's charter (below) is
  written to start from these four questions directly rather than rediscover
  them.
- **Single-platform (macOS/arm64) evidence only**, across all four tickets.
  **Decision: accepted limitation, does not block G0.** G0's criteria do not
  require multi-platform reproduction. Flagged as a trigger for revisiting
  this decision (below) if a later Linux/amd64 reproduction diverges.

## Decision

**G0 passes.** T1 (TF-002: measurement contracts and representative
fixtures) is unblocked and may begin. No Risk Lab experiment (E01-E08) may
begin before its T1 dependency above is satisfied, regardless of this
decision.

## Consequences and deliberately unsupported cases

- This decision does not certify the prototype's cache-before-provision
  ordering, its local admission exclusivity, or its two Fable-related test
  gaps as acceptable for the *product*. It certifies only that T0's job —
  evidencing the prototype's current state — is done, and hands the
  unresolved substance to E04 (cache/ordering) and to residual-risk tracking
  (test gaps).
- This decision does not initialize a root production Go module, and does
  not authorize one. Per roadmap section 3 rule 2 and section 24 item 8, that
  waits for Gate 1.
- This decision does not claim Linux/amd64 reproducibility; all four
  evidence tickets are macOS/arm64-only.
- Risk Lab start order above is a plan, not an authorization to start work
  immediately — every experiment still waits on its stated T1 dependency.

## Trigger for revisiting this decision

- A Linux or amd64 reproduction of the T0 gate evidence fails where macOS/arm64
  passed.
- T1's purpose-built W1 fixture (TF-002.01) turns out to differ materially
  from the `.taskflow/main.go` fixture TF-001.03 measured (e.g. by adding an
  explicit aggregate join node), invalidating the graph-size/startup baseline
  as a point of comparison.
- New evidence contradicts any "Proven" classification in
  `docs/evidence/t0/package-inventory.md` section 3.
- E04 finds the cache-identity/acquisition-ordering problems characterised in
  TF-001.04 are worse, or different in kind, than described here.

## Contracts now allowed to stabilize

None. No plan, schema, cache, provider, or SDK contract stabilizes at G0.
T0's own evidence-file convention (`docs/evidence/<tranche>/<doc>.md` plus a
`raw*/` subdirectory per ticket) may be informally reused by T1 evidence
tickets for consistency, but TF-002.04 (define the benchmark evidence format
and runner) remains the sole owner of any standardized, versioned benchmark
result format; this decision does not preempt it.
